本セクションでは、負荷試験の基本設計における「利用ツールの選定」について説明します。

## ツールを利用した負荷試験
負荷試験は、サーバに一定の負荷がかかっている状態で目標の性能を達成できるかを確認する試験です。負荷試験では「一定の負荷」を実現するために、対象のサーバへ多数のリクエストを発行し、その結果を計測して期間全体で集計する必要があります。

**負荷試験で用いるツール例**
- JMeter
- AWS Distributed Load Testing (DLT)
- BlazeMeter

## JMeter
JMeterは負荷試験を行うためのオープンソースのテストツールで、Apacheが提供しています。ローカルPCで動作するGUIベースのアプリケーションで、CLIでの実行にも対応しています。

JMeterではGUIを用いてテスト計画を作成できます。作成したテスト計画はJMeter上で実行可能で、実行後の結果集計や詳細ログ出力にも対応しています。

:::message
テスト計画には対象のエンドポイントやリクエストパラメータのほか、実施期間や並列数などを定義できます。
:::

JMeterで作成したテスト計画は拡張子`.jmx`のファイル形式で出力できます。jmxファイルを共有すれば、チームメンバーが同じテストを再現できるため、共同作業が円滑になります。

多くのプロジェクトでJMeterは長らく負荷試験の第一選択肢として使われていますが、近年は後発の負荷試験ツールも普及しています。多くのツールがjmx形式の読み込みに対応していることから、JMeterで作成したテスト資産は他ツールでも活用できます。

このように JMeter は、「サーバに負荷をかける負荷試験実施ツール」と「jmx ファイルを作成するツール」との２つの側面を持っているといえます。

### JMeterの実行上限
JMeterはエンドポイントへ並列で大量のリクエストを送信できますが、ローカルPCで動作するためCPUやメモリ、ネットワーク帯域に依存します。これらのリソースがボトルネックになると、テスト結果が不安定になりエラーが増えることがあります。

:::message
並列処理の上限は、様々な要因によって決まるため、一意にいくつまでが安定ということが言えません。
主に「手許PCの性能(CPU/RAM)」「jmxシナリオの複雑さ」「ネットワーク環境」などが並列処理数に影響します。
:::

:::message
一般に100程度の並列は問題なく安定稼働するケースが多いです。500を超える並列が必要な場合は分散実行環境の利用を検討してください。
:::

高い負荷が要求される場合、ローカルJMeterだけでは対応できないため、AWS DLTなどの分散実行環境を検討します。

## AWS DLT (Distributed Load Testing)
AWS DLT は AWS 製の負荷試験ツールでです。VPC 内に ECS 環境を構築してクラウドベースの負荷試験実施環境を構築することができます。

https://aws.amazon.com/solutions/implementations/distributed-load-testing-on-aws/

テストのシナリオには jmx ファイルが利用可能となっており、JMeter で作成したテストファイルを投入してクラウド環境上で負荷試験を実施することができます。

DLT は必要に応じて複数の ECS を構築し、より多くの並列処理を可能としている分散実行環境となっています。
CloudFomation ベースのテンプレートが公開されているため、AWS に関する知見が少ない人でも簡単に構築でき、かつ Build & Destory を簡単に進めることができます。

AWS DLT を利用した際のコストについては、以下公式のドキュメントにまとめられています。

https://docs.aws.amazon.com/ja_jp/solutions/latest/distributed-load-testing-on-aws/cost.html

DLT の環境はサーバレスな構成をベースにしており、ほとんどのコストは「使った分だけ」で抑えられるように設計されています。

## Blazemeter 
Blazemeter もクラウドベースの負荷試験ツールです。AWS の DLT と違ってインフラを自分で構築する必要がないため、SaaS サービスとして利用できるのが特徴です。
https://www.blazemeter.com/

Blazemeter も テストのシナリオに jmx ファイルを利用することができ、JMeter で作成したテストファイルを投入してクラウド環境上で負荷試験を実施することができます。

負荷試験の分散実行にも対応しており、異なるリージョンから複数台の環境で柔軟にリクエストを発行することが可能です。
結果のフォーマットが DLT よりも詳細でわかりやすい、といった特徴もあります。

Blazemeter の料金は以下のページから確認できます。
https://www.blazemeter.com/pricing

Blazemeter ではテスト実施に係るクレジットを VUH という単位でカウントしており、Proプランでは 80,000 VUH/year が利用可能です。
仮想ユーザー1人が1時間テストを実行することを「1 VUH」としてカウントするため、例えば、100ユーザの並列処理で1時間テストを実行すると 100 VUHが消費されます。

## ツールの選定基準
ツール選定を行う際には、まず分散環境が必要かどうかを判断します。

例えば、100並列を基準にした場合、応答時間が0.8秒のエンドポイントは約125 RPS、1.5秒のエンドポイントは約66 RPSを実現できます。要求されるRPSが高く、並列が100を超えそうであれば分散環境を前提に設計します。

分散環境構築はAWS DLTが一般的ですが、AWSの知見が少ない場合はBlazeMeterなどのSaaSソリューションを選ぶのも有効です。いずれもコストが発生するため、費用負担や概算をクライアントと事前に合意しておきましょう。

## 制約の説明
ツールを使った負荷試験では、ツールを使って擬似的に負荷環境を作るため、実際のユーザリクエストによって生じる負荷とはいくつかの差異があります。これらの差異は事前に説明し、クライアントの合意を得たうえで実施する必要があります。

主な差異例:
- テストで用いるリクエストはあらかじめ定義された一定のパラメータを繰り返すことが多く、実際の多様なパラメータ変動を完全には再現できない。
- 実際のユーザは複数エンドポイントへ散発的にリクエストを送るため、リクエスト順や連携条件により想定外の負荷が発生する可能性がある。
- ネットワーク環境やクライアント端末の多様性（帯域、遅延、TLSハンドシェイク等）を完全には模擬できない。

これらを踏まえ、テスト設計時にカバレッジの限界や前提条件を明示し、結果の解釈に必要な注意点を報告書へ記載してください。

## 検証対象  
検証対象の定義では、負荷試験で実際に検証を行う対象（エンドポイント）についての定義を進めます。

負荷試験で対象として定義するエンドポイントについては、大きく以下の３つの観点で整理が必要です。

- 単一リクエスト : 単一のエンドポイントにリクエストを繰り返し実施して実施する試験。
- 単一シナリオ : ユーザの導線に沿って発生する一連のリクエストを「シナリオ」として、シナリオに沿ったリクエストを繰り返し実施する試験。
- 複合シナリオ : 複数のシナリオを同時に並列で繰り返して行う試験。

これらは３つのうちどれを採用するか、というものではなく、
３つそれぞれについて、各どのように実施するかを検討する必要があります。

### 単一リクエスト
単一リクエストの試験では、画面一覧や API 一覧をベースに、負荷試験の対象エンドポイントを選定します。

システムが実装するすべての画面やすべての API について負荷試験を実施するのは現実的でないため、耐負荷性能の重要性の観点や実装の観点から適切なエンドポイント選定を実施します。

一般に Read 系のエンドポイントへの負荷試験は実施が簡単ですが、CREATE/UPDATE/DELETEなどの操作を含むエンドポイントへの負荷試験は、実施手順が複雑になりがちです（パラメータの準備など）。
実際に負荷試験で実施できる期間やリソースに沿って、対象エンドポイントの選定は慎重に進める必要があります。

### 単一シナリオ
単一シナリオの試験では、システム上のユーザ行動のパターンに沿ってシナリオを定義します。
EC システムにおける購入フローや、会員管理システムにおける登録フローなどがそれにあたり、通常一つのシナリオの中で複数のエンドポイントへのリクエストが順に行われる構成を取ります。

こちらも考えうるすべてのユーザ導線についてシナリオを定義するのは現実的でないため、耐負荷性能の重要性の観点や実装の観点から適切なシナリオ選定を実施します。

### 複数シナリオ
システムの機能が多機能に渡るケースなどで、個別の単一シナリオの検証ではシステム全体の負荷性能に不安があるケースで複数シナリオの試験を実施します。

同時に実行すべきシナリオが複数あるパターンでは重要な試験になりますが。実施の負担は大きいため、前述の単一リクエスト・単一シナリオベースの試験で負荷性能を担保できるのであれば割愛するのが良いでしょう。

## 検証対象定義の勘所
検証対象の選定は、そのまま負荷試験の規模感に直結してくるため、意思決定には慎重な議論が必要です。

一般には、実施が簡単な順に 単一リクエスト、単一シナリオ、複合シナリオのパターンになるため、負荷試験対象の選定方針としては、以下のような考え方で進めるとよいでしょう。

- エンドポイントベースでの負荷試験は、単一リクエストをベースに網羅する。
- ユーザ体験上、特別な重要性や KPI を設けることに必然性があるようなシナリオでのみ単一シナリオ試験を実施する。
  - 前提としてエンドポイント単位での負荷性能は、単一リクエストベースで担保されていることを確認したうえで、「なぜシナリオベースの追加検証を実施するか」については明らかにしておく
- システム規模が複雑で、単一シナリオでリリース判断が難しい場合には、複合シナリオの導入を検討する
  - 複合シナリオは実施負担が大きいため、より簡便に実施できるような性能指標面での調整や対象シナリオの選定は工夫する。

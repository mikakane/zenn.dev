## 報告フォーマット
通常負荷試験では、負荷試験の作業記録として「負荷試験作業報告書」のようなものを作成することが多いでしょう。

報告書のベースフォーマットはプロジェクトによって様々だと思いますが、負荷試験のエビデンスとしてどのようなフォーマットでどのようなデータが必要になるかは。事前のすり合わせが必要です。

### 負荷試験のエビデンス
負荷試験の実施記録として利用可能なエビデンスには、次のようなデータがあります。

- サマリベースのエビデンス
    - 実施した日時と負荷設定
    - 負荷試験の結果として、実施期間における性能評価値
        - RPSやリクエスト数
        - 平均応答時間とパーセンタイルごとの応答時間
        - エラー率 など
- 詳細ベースのエビデンス
    - 負荷試験で実施した個別リクエストのスナップショット
- 対象環境上のエビデンス
    - 負荷試験中、対象の環境に適切に負荷がかかっていたことを証明するインフラのモニタ指標
    - 対象インフラサーバ上のサーバログ

jMeter を利用した試験では、サマリのレポートは簡単に出力することが可能で、また個別リクエストのスナップショットも設定次第で取得することが可能です。
クラウドベースの負荷試験ツールでも同様のエビデンスが取得可能な他、サマリについてはグラフィカルにグラフで取りまとめてくれるなど、検証結果の可視化にも貢献してくれます。

### 負荷試験のエビデンスをどう定義するか？
負荷試験の結果として、最低限サマリベースのエビデンスは添付しておく必要があります。
数値の羅列では視覚的に理解しづらい部分もあるため、グラフ等を利用して目標指標に対する到達度合いをわかりやすく訴求しておくのが良いでしょう。

サマリで取得できるデータの種類についてはツールごとの特徴があるため、ツールで取得可能な性能評価値を事前に列挙して種類の合意を取っておくのが良いでしょう。ツールで取得できない類の評価値について後からクライアント要望を出された場合、膨大な詳細エビデンスから自力で集計処理を行うのは非常に困難な作業になります。

詳細ベースのエビデンスは、大規模な負荷試験では膨大なファイルサイズとなるケースも多いため割愛できるのであれば割愛するに越したことはないでしょう。
対象インフラサーバ上のサーバログについても、時々求められるケースがありますが、やり取りが面倒無うえに本質的な意味はないため、断っておくにこしたことはないでしょう。

## AWS DLT のテストレポート
AWS DLT のテストレポートの様式については、公式のドキュメント上で詳しく説明がされています。
https://docs.aws.amazon.com/ja_jp/solutions/latest/distributed-load-testing-on-aws/test-results.html

> - Average response time - テストによって生成されたすべてのリクエストの平均応答時間 (秒)
> - Average latency - テストによって生成されたすべてのリクエストの平均レイテンシー (秒)
> - Average connection time - テストで生成されたすべてのリクエストについて、ホストへの接続にかかった平均時間 (秒)
> - Average bandwidth - テストで生成されたすべてのリクエストの平均帯域幅
> - Total count - リクエストの総数
> - Success count - 成功したリクエストの総数
> - Error count - エラーの総数
> - Requests per second - テストで生成されたすべてのリクエストの 1 秒あたりの平均リクエスト数
> - Percentile - テストの応答時間のパーセンタイル値。最大応答時間は 100%、最小応答時間は 0%。
